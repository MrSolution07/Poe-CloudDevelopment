## Section A — Advanced Filtering

### A.1 EventType Lookup Table

A new `EventTypes` lookup table was added to the database with eight predefined categories to classify events. The table is defined in `Database/Schema.sql` and seeded by EF Core at application startup.

| EventTypeId | Name |
|---|---|
| 1 | Conference |
| 2 | Wedding |
| 3 | Concert |
| 4 | Workshop |
| 5 | Exhibition |
| 6 | Corporate |
| 7 | Birthday Party |
| 8 | Other |

The `Events` table contains an `EventTypeId INT NULL` foreign key column that links each event to its type category. When a booking specialist creates or edits an event, they select an event type from a dropdown populated from this table.

**Database script evidence** (`Database/Schema.sql`):

```sql
IF NOT EXISTS (SELECT * FROM sys.tables WHERE name = 'EventTypes')
BEGIN
    CREATE TABLE EventTypes (
        EventTypeId   INT IDENTITY(1,1) PRIMARY KEY,
        Name          NVARCHAR(100) NOT NULL
    );
END;

-- Events table includes EventTypeId FK
EventTypeId INT NULL,
CONSTRAINT FK_Events_EventTypes FOREIGN KEY (EventTypeId)
    REFERENCES EventTypes(EventTypeId)
```

The `Venues` table also includes an `IsAvailable BIT NOT NULL DEFAULT 1` column added to support availability filtering in the booking overview.

### A.2 Filter by Event Type

The Booking Overview allows the booking specialist to filter all bookings by event category using the `EventType` dropdown. When an event type is selected, only bookings whose associated event matches that type are displayed.

**Controller evidence** (`EventEaseApp/Controllers/BookingsController.cs`):

```csharp
if (model.EventTypeId.HasValue)
{
    var eventTypeId = model.EventTypeId.Value;
    var eventIds = _context.Events
        .Where(e => e.EventTypeId == eventTypeId)
        .Select(e => e.EventId);
    query = query.Where(b => eventIds.Contains(b.EventId));
}
```

**View evidence** (`EventEaseApp/Views/Bookings/Overview.cshtml`):

```html
<select name="EventTypeId" class="form-select">
    <option value="">All types</option>
    @foreach (var et in Model.EventTypes)
    {
        <option value="@et.EventTypeId">@et.Name</option>
    }
</select>
```

The `BookingSearchViewModel` (`EventEaseApp/Models/BookingSearchViewModel.cs`) carries the selected event type as a nullable integer (`int? EventTypeId`) so the filter is entirely opt-in — when no type is selected the filter is skipped and all bookings are returned.

### A.3 Filter by Date Range

The Booking Overview provides two date inputs — Event Date From and Event Date To — that restrict results to bookings whose associated event falls within the specified range. Either bound can be used independently.

**Controller evidence** (`EventEaseApp/Controllers/BookingsController.cs`):

```csharp
if (model.DateFrom.HasValue)
    query = query.Where(b => b.EventDate >= model.DateFrom.Value);

if (model.DateTo.HasValue)
    query = query.Where(b => b.EventDate <= model.DateTo.Value);
```

**View evidence** (`EventEaseApp/Views/Bookings/Overview.cshtml`):

```html
<input type="date" name="DateFrom"
       value="@Model.DateFrom?.ToString("yyyy-MM-dd")" class="form-control" />
<input type="date" name="DateTo"
       value="@Model.DateTo?.ToString("yyyy-MM-dd")" class="form-control" />
```

### A.4 Filter by Venue Availability

The booking specialist can filter the Booking Overview to show only bookings associated with venues that are currently available or currently unavailable.

**Model evidence** (`EventEaseApp/Models/Venue.cs`):

```csharp
[Display(Name = "Available")]
public bool IsAvailable { get; set; } = true;
```

**Controller evidence** (`EventEaseApp/Controllers/BookingsController.cs`):

```csharp
if (model.IsAvailable.HasValue)
    query = query.Where(b => b.IsAvailable == model.IsAvailable.Value);
```

**View evidence** (`EventEaseApp/Views/Bookings/Overview.cshtml`):

```html
<select name="IsAvailable" class="form-select">
    <option value="">All</option>
    <option value="true">Available</option>
    <option value="false">Unavailable</option>
</select>
```

All three filter conditions are applied as optional LINQ predicates on the `BookingDetailViewModel` query. When combined, they produce an AND-filtered result set. Filters also work alongside the existing search-by-Booking-ID-or-Event-Name functionality from Part 2.

### C.2 Component Discussion

#### Azure Services

**Azure App Service (Web App)**

Azure App Service is the PaaS hosting service used to run the EventEase ASP.NET Core MVC application. As a fully managed compute platform, App Service removes the need to provision, configure, or maintain virtual machines or operating systems (Microsoft, 2026a). Built-in .NET runtime support, HTTPS enforcement, environment variable configuration, and deployment via zip deploy made it the most practical hosting choice for this project.

The application is deployed to the Switzerland North region under the resource group `EventEase-rg` with the app name `st10538419-eventease`. Deployment is automated via the `deploy-to-azure.sh` script, which builds a Release-mode publish package and pushes it to Azure using the `az webapp deploy` CLI command.

*Why chosen:* App Service provides a managed runtime environment with no infrastructure overhead. As a PaaS offering, it handles OS patching, SSL certificates, load balancing, and scaling — concerns that would require significant operational investment if managed on raw virtual machines (IaaS). For a growing company like EventEase that needs to scale quickly without a large infrastructure team, PaaS is the appropriate model.

*Alternative:* **Azure Container Apps** would allow EventEase to containerise the application in Docker and deploy to a managed Kubernetes-based environment (Microsoft, 2026f). This would provide container-level isolation and more fine-grained scaling rules. However, it introduces the operational overhead of building and maintaining container images, which was not justified at this stage of the project.

---

**Azure SQL Database**

Azure SQL Database is the fully managed relational database service used to store all EventEase domain data — venues, events, bookings, event types, booking requests, and ASP.NET Identity user records (Microsoft, 2026b). The service provides automated backups, transparent data encryption at rest, and built-in high availability without manual database administration.

The schema is managed through two complementary mechanisms: EF Core's `EnsureCreated()` method creates tables and constraints from the code-first model on first startup, and `Database/Schema.sql` provides an idempotent script for SQL views and any manual schema verification via the Azure SQL Query Editor.

*Why chosen:* The EventEase data model is inherently relational. Bookings link events to venues through foreign keys; double-booking prevention relies on a `UNIQUE (VenueId, BookingDate)` index; the booking overview joins four tables in `vw_BookingDetail`. These requirements are naturally and efficiently expressed in a relational database with SQL join semantics, ACID transaction guarantees, and declarative integrity constraints.

*Alternative:* **Azure Cosmos DB** would be a viable alternative for scenarios requiring global distribution and horizontal partitioning at massive scale (Microsoft, 2026c). Cosmos DB stores data as schema-flexible JSON documents and offers configurable consistency models from strong to eventual consistency. For EventEase's current scale, denormalising booking, event, and venue data into a single document per booking would remove the need for joins — but would introduce challenges in keeping the embedded venue and event data consistent when records are updated. The relational model remains appropriate at this stage.

---

**Azure Blob Storage**

Azure Blob Storage is the object storage service used to store venue and event images uploaded by booking specialists (Microsoft, 2026d). Images are uploaded to two named containers — `venue-images` and `event-images` — and served to the browser via their public blob URL stored as `ImageUrl` in the database. When a record is edited or deleted, the corresponding blob is removed by `BlobStorageService.DeleteImageAsync()`.

*Why chosen:* Storing images in Blob Storage rather than as file system paths or database binary columns ensures that images remain accessible across multiple App Service instances (supporting horizontal scale-out), are managed independently of application deployments, and benefit from Azure's geo-redundant storage replication. Blob Storage is purpose-built for unstructured binary content at scale.

*Alternative:* An **Azure CDN** (Content Delivery Network) layer in front of Blob Storage would cache images at global edge nodes, reducing latency for users accessing the application from different regions. This is not required for the current single-region deployment but would be the recommended first enhancement as EventEase expands internationally.

**Azure Cosmos DB — Theoretical Consideration**

Azure Cosmos DB is a globally distributed, multi-model NoSQL database service that differs fundamentally from traditional relational databases (Microsoft, 2026c). Where relational databases enforce a fixed schema with tables, columns, and foreign key constraints, Cosmos DB stores schema-flexible JSON documents that can vary in structure between records. Cosmos DB offers multi-region replication with configurable consistency levels (Strong, Bounded Staleness, Session, Consistent Prefix, Eventual), automatic indexing on all document properties, and guaranteed sub-10-millisecond latency at any scale through horizontal partitioning.

The core architectural difference is that Cosmos DB is designed for horizontal partitioning across many servers, whereas relational databases traditionally scale vertically (larger servers) and use sharding only as an advanced pattern. Cross-partition queries in Cosmos DB are more expensive than single-partition queries, so data modelling requires embedding frequently co-accessed data together in a document, rather than normalising it across tables and joining on read.

For EventEase's current phase, Azure SQL Database is the correct choice because the booking domain requires multi-table joins, unique constraints, and ACID transactions. Cosmos DB would become more appropriate if the platform needed to serve real-time venue availability queries to millions of users across multiple continents simultaneously, where Cosmos DB's global distribution and elastic partitioning would outweigh the complexity of managing a denormalised document model.

#### Development Technologies

**ASP.NET Core MVC (.NET 10)**

ASP.NET Core MVC is the web framework used to build EventEase (Microsoft, 2026e). The Model-View-Controller pattern separates domain entities and validation rules (Models), HTML rendering (Razor Views), and HTTP request orchestration and business logic (Controllers). .NET 10 is the current framework version, providing performance improvements, built-in dependency injection, native Linux support on Azure App Service, and modern C# language features.

*Alternative:* A Blazor WebAssembly front-end with an ASP.NET Core Web API backend would provide a more interactive, SPA-like experience without a JavaScript framework. For this project, server-rendered Razor MVC was preferred for its straightforward request-response model and reduced client-side complexity.

---

**Entity Framework Core**

EF Core is the object-relational mapper that translates between C# domain models and Azure SQL tables (Microsoft, 2026g). `EventEaseContext` extends `IdentityDbContext<ApplicationUser>` to manage both the application domain and ASP.NET Identity tables in one database context. The fluent API in `OnModelCreating` configures primary keys, foreign keys, unique indexes, default values, and column types — translating business rules directly into database schema constraints.

*Alternative:* Dapper is a lightweight micro-ORM that maps raw SQL results to C# objects without a full object graph. It provides more precise control over complex queries but requires manual SQL management for schema changes. EF Core's LINQ-based query composition was preferred for the filter chain in `BookingsController.Overview`.

---

**SixLabors.ImageSharp**

ImageSharp is a cross-platform image processing library used to validate, resize, and re-encode uploaded image files before blob storage (SixLabors, 2024). It was selected because `System.Drawing.Common` — the legacy .NET image library — is not supported on Linux-based App Service environments where the application runs. ImageSharp provides the same processing capabilities in a fully cross-platform implementation, validating file types, resizing to max 1920 px, compressing to JPEG quality 84 or PNG, and enforcing output size limits.

**Azure Logic Apps — Theoretical Consideration**

Azure Logic Apps is a serverless workflow automation service that connects applications, data, and services through event-driven workflows without managing infrastructure (Microsoft, 2026h). When designing Logic App workflows that process sensitive data — such as customer names, email addresses, and booking details in EventEase — the following key considerations apply.

*Secure Inputs and Outputs:* By default, Logic App run history stores all action inputs and outputs for diagnostics. Sensitive fields must be protected by enabling the "Secure Inputs" and "Secure Outputs" properties on actions handling personal information, which obfuscates the data from run history logs.

*Managed Identity:* Connectors to Azure resources (SQL Database, Blob Storage, Service Bus) should authenticate via System-Assigned or User-Assigned Managed Identity rather than stored connection strings. This eliminates hardcoded credentials from the workflow definition and rotates authentication automatically (Microsoft, 2026h).

*Minimal Data:* Workflows should pass only the data required for each individual step. Full customer records should not be propagated through connector chains where only a booking ID is needed.

*Audit Logging:* Logic Apps integrate with Azure Monitor Diagnostic Logs, producing audit trails of all workflow triggers and actions — supporting compliance with GDPR and POPIA requirements.

For EventEase, a Logic App could automate the processing of `BookingRequests` — sending confirmation emails to customers and alerting booking specialists — while applying these considerations to protect customer personal data throughout the automated flow.

---

**Azure Event Grid — Theoretical Consideration**

Azure Event Grid is a fully managed event-routing service built on a publish-subscribe model (Microsoft, 2026i). Publishers emit events describing state changes; subscribers react independently. Event Grid guarantees at-least-once delivery with configurable retry policies and dead-letter destinations, making it a foundation for resilient, event-driven architectures.

Combining Event Grid with other Azure services creates robust workflows for EventEase:

*Event Grid + Azure Functions:* When a booking is created, the application publishes a `BookingCreated` custom event. An Azure Function subscribed to this event sends a confirmation email and generates a PDF receipt asynchronously, without coupling these operations to the booking HTTP request or blocking the user's response.

*Event Grid + Azure Blob Storage (native):* Blob Storage natively publishes `Microsoft.Storage.BlobCreated` events to Event Grid when images are uploaded. An Azure Function or Logic App subscribed to this topic can automatically generate image thumbnails, run content moderation, or update a search index — all triggered by the upload itself without polling.

*Event Grid + Azure Service Bus:* For high-throughput scenarios requiring guaranteed delivery and message ordering, Event Grid routes events to a Service Bus queue. Multiple downstream services (email, analytics, reporting) each consume from their own Service Bus subscription, ensuring no event is dropped even if a service is temporarily unavailable.

The architectural value of Event Grid is decoupling: the EventEase application publishes events about what happened, and subscribers decide independently how to react. This makes it possible to add new capabilities — notifications, audit logging, analytics — without modifying the core application code (Microsoft, 2026i).

### C.3 Project Reflection

#### Development Journey

Developing the EventEase Venue Booking System across three parts of this Portfolio of Evidence has been the most technically comprehensive project I have completed during my studies. The project required simultaneous work across multiple layers — database design, MVC development, cloud service integration, and deployment automation — while maintaining consistency between those layers as requirements evolved from one part to the next.

#### Part 1: Foundation and Key Decisions

The most consequential decision in Part 1 was the initial database schema. I chose to include the `EventTypeId` foreign key on Events and the `IsAvailable` flag on Venues from the beginning, even though they were not required until Part 3. Reading the full POE requirements before writing any code paid off directly: when Part 3 arrived, the filters could be implemented without modifying the existing schema or running any migrations.

I also chose to enforce the double-booking rule at both the application layer (`ValidateBookingAsync()`) and the database layer (`UNIQUE (VenueId, BookingDate)` constraint). This defence-in-depth approach — the same business rule enforced at two independent points — ensured that concurrent requests or direct database modifications could not create double bookings even if the application logic was bypassed.

Deploying to Azure for the first time taught me a critical limitation I had not encountered before: `EnsureCreated()` creates EF Core entity tables but does not execute raw SQL to create views. The `vw_BookingDetail` view needed for Part 2's Booking Overview had to be created separately via the Azure SQL Query Editor. Understanding this gap between EF Core's schema management and full SQL Server DDL management shaped how I documented the deployment process and why `Database/Schema.sql` exists as a separate idempotent script.

#### Part 2: Cloud Integration Challenges

Integrating Azure Blob Storage required implementing a multi-environment configuration strategy I had not used at this depth before. The `BlobStorageService.IsConfigured` pattern — where the service starts in a disabled state when no valid connection string is present, rather than throwing at startup — came from the frustration of early deployment failures. Understanding the distinction between `appsettings.json` (local defaults), `appsettings.Development.local.json` (gitignored local developer secrets), and App Service Application Settings (production configuration) is a cloud development pattern I would now apply from the start of any cloud project.

The ImageSharp library was not chosen purely by preference. When I first tested the deployed application on the Linux-based App Service environment, `System.Drawing.Common` produced runtime errors because Microsoft no longer supports it on non-Windows platforms. Replacing it with ImageSharp resolved the issue and reinforced the importance of validating dependency compatibility with the target deployment environment before implementing features, not after.

#### Part 3: Filters and Architecture Insight

Implementing the three advanced filters in Part 3 was technically straightforward because the data model had been designed correctly in Part 1. The nullable filter properties on `BookingSearchViewModel` compose naturally into LINQ query chains, and the `BookingDetailViewModel` already projected `EventTypeName` and `IsAvailable` fields. This demonstrated the practical value of thoughtful upfront data modelling: a Part 3 feature required writing new query conditions, not redesigning the data model.

#### Broader Lessons Learned

The most significant shift in my understanding of cloud development is the distinction between *deploying to the cloud* and *designing for the cloud*. In Part 1, I treated Azure as a remote hosting environment. By Part 3, I understood that cloud-native applications are designed with specific properties in mind: statelessness (so multiple App Service instances serve requests without shared local state), retry logic (for transient Azure SQL connection failures), environment-based configuration (so no secrets are embedded in source code), and separation of compute from storage (images live in Blob Storage, not with the application).

The PaaS model provided by Azure App Service and Azure SQL Database allowed me to focus entirely on application logic rather than infrastructure management. I did not configure servers, install runtimes, manage SSL certificates, or plan database backup schedules — all of this was handled by the platform. As EventEase scales, this becomes increasingly valuable: horizontal scaling of the App Service plan, adding a deployment slot for zero-downtime releases, and configuring database geo-replication are all available without provisioning infrastructure.

#### What I Would Do Differently

If I were starting this project again, I would adopt **EF Core Migrations** from the first commit rather than `EnsureCreated()`. Migrations provide versioned, incremental schema evolution tracked in source control. The inability to evolve the schema automatically — and the need to manually run SQL view scripts via the Query Editor — was the single most disruptive technical limitation across all three parts. I would also configure **Azure Key Vault** for secrets management from the start rather than relying on App Service Application Settings, and I would create a dedicated **xUnit test project** to automate the verification of critical business rules such as double-booking prevention and deletion restriction, reducing reliance on manual testing after each deployment.
