## Section A - Advanced Filtering

### A.1 EventType Lookup and Venue Availability

Part 3 required the booking search to be extended with event type, date range and venue availability filters. To support this, the application includes an `EventTypes` lookup table with predefined event categories: Conference, Wedding, Concert, Workshop, Exhibition, Corporate, Birthday Party and Other. Events link to the lookup table through `Events.EventTypeId`, while venues include an `IsAvailable` field so booking specialists can filter bookings according to the availability status of the linked venue.

These database changes are represented in the application models (`EventType`, `Event`, and `Venue`) and in the database scripts (`Database/Schema.sql` and `Database/script.sql`). The `EventEaseContext` seeds the event type values so the dropdown is available when the application starts.

### A.2 Filter by Event Type

The Booking Overview page includes an Event Type dropdown populated from the `EventTypes` table. When a booking specialist selects a category, the `BookingsController.Overview` action applies a LINQ filter so only bookings linked to events in that category are returned. This improves usability because staff can narrow bookings by operational category, such as weddings or conferences, instead of scanning all booking rows manually.

### A.3 Filter by Date Range

The Booking Overview page provides `DateFrom` and `DateTo` fields. These fields filter bookings according to the event date of the linked event. Either field can be used independently, which means a booking specialist can view bookings after a selected date, before a selected date, or between two selected dates. This is useful for weekly scheduling, monthly reporting, and identifying upcoming event load.

### A.4 Filter by Venue Availability

The venue availability filter uses the `Venues.IsAvailable` field. Booking specialists can show bookings linked to available venues, unavailable venues, or all venues. This is valuable because the organisation can mark venues as unavailable for maintenance or operational reasons and still understand which bookings are affected.

All filters work with the existing Part 2 search by booking ID or event name. When more than one filter is selected, the system applies them together, producing a more precise result set.

### C.2 Component Discussion

#### Azure App Service

Azure App Service was used to host the ASP.NET Core MVC application. It was appropriate because it is a Platform as a Service (PaaS) hosting model that manages the web server, runtime, SSL support, scaling options and deployment endpoint. This allowed the project to focus on application functionality instead of virtual machine maintenance. Microsoft (2026a) explains that App Service is designed for hosting web apps, REST APIs and mobile back ends with built-in deployment and scaling features.

An alternative would be Azure Virtual Machines, but this would require managing the operating system, IIS/Kestrel hosting, security patching and scaling manually. Azure Container Apps could also be used if the application were packaged as a container, but App Service was simpler and better aligned with the POE requirements.

#### Azure SQL Database

Azure SQL Database was used to store structured data for venues, events, bookings, event types, booking requests and ASP.NET Identity users. A relational database was suitable because the EventEase domain depends on clear relationships and referential integrity. A booking must reference a valid event and venue, and deletion rules must protect records with active bookings. Azure SQL also supports SQL views, constraints and familiar T-SQL queries, which made it suitable for the consolidated `vw_BookingDetail` view. According to Microsoft (2026b), Azure SQL Database is a managed relational database service that provides high availability, backups and scaling options.

An alternative would be Azure Cosmos DB, especially if the application needed globally distributed, flexible JSON documents. However, for this project, Azure SQL was the better fit because the data is strongly relational and the rubric required database tables, relationships and query editor evidence.

#### Azure Blob Storage

Azure Blob Storage was used for venue and event image uploads. Images are unstructured binary objects, so storing them inside SQL tables would increase database size and reduce efficiency. Blob Storage separates media storage from structured booking data and gives each uploaded image a URL that can be saved in the database. Microsoft (2026c) describes Blob Storage as an object storage solution for large amounts of unstructured data.

An alternative would be storing images in the web app's file system, but this is not suitable for cloud deployment because App Service instances can be replaced or scaled. Another alternative would be Azure Files, but Blob Storage is simpler and more appropriate for public web images.

#### ASP.NET Core MVC

ASP.NET Core MVC was used because the POE required an ASP.NET Core web application and because MVC clearly separates models, views and controllers. This separation helped organise the project: models represent database entities, controllers contain request logic, and Razor views render the user interface. Microsoft (2026d) explains that ASP.NET Core MVC supports testable, maintainable web applications through the model-view-controller pattern.

An alternative would be Blazor, which could provide a more interactive client experience. However, MVC was more suitable for the POE because it aligns with the required CRUD-based web application structure and integrates cleanly with Razor forms and EF Core.

#### Entity Framework Core

Entity Framework Core was used as the Object Relational Mapper between the C# application and Azure SQL Database. It allowed the application to query and update tables through strongly typed C# models instead of writing SQL in every controller. EF Core also allowed relationships, constraints, seed data and the keyless booking detail view to be represented in the application. Microsoft (2026e) describes EF Core as a modern data access technology for .NET.

An alternative would be Dapper or direct ADO.NET SQL commands. Those options may provide more explicit SQL control, but EF Core was more productive for this project because most screens were standard CRUD workflows.

#### SixLabors ImageSharp

SixLabors ImageSharp was used to process uploaded images before sending them to Blob Storage. It is cross-platform, which matters because Azure App Service may run on Linux. The library helped resize and compress images so large uploads do not waste bandwidth or storage. SixLabors (2024) describes ImageSharp as a modern cross-platform 2D graphics library for .NET.

### C.3 Theoretical Discussion

#### Cosmos DB Compared with Traditional Databases

Azure Cosmos DB differs from traditional relational databases mainly in its data model, distribution model and scaling approach. Traditional relational databases such as SQL Server store data in structured tables with predefined schemas, primary keys, foreign keys and relationships. They are strong when the data model is relational and consistency across records is important, such as bookings linked to venues and events.

Cosmos DB is a globally distributed NoSQL database that stores data using flexible models such as documents, key-value, graph or column-family APIs depending on the selected interface. Microsoft (2026f) explains that Cosmos DB offers turnkey global distribution, elastic scalability, low-latency reads and writes, and multiple consistency levels. This makes it suitable for applications that need high availability across regions, flexible JSON documents or very large scale.

The trade-off is design complexity. In Cosmos DB, developers often model data around access patterns and partition keys rather than normalised relationships. Joins and relational constraints are not used in the same way as SQL databases. For EventEase, Cosmos DB could be useful for future audit logs, customer activity feeds or globally distributed enquiry records, but Azure SQL Database remains more appropriate for the main booking system because bookings require relational integrity and conflict prevention.

#### Logic Apps Handling Sensitive Data

Azure Logic Apps can automate workflows by connecting services and triggering actions when events occur. When a Logic App handles sensitive data, the design must protect confidentiality, integrity and access control throughout the workflow. Microsoft (2026g) notes that Logic Apps can integrate with Azure services and external systems, which means a workflow can easily move data across many connectors if it is not carefully controlled.

The first consideration is identity and access. Workflows should use managed identities where possible so secrets are not stored directly in workflow definitions. If connection strings or API keys are required, they should be stored in Azure Key Vault and referenced securely. The second consideration is least privilege. Each connector should only have the permissions needed for its task, such as sending an email or reading a single queue message.

The third consideration is data minimisation. A Logic App should pass only the fields needed for each step. For example, an EventEase booking confirmation workflow may only need the booking ID, customer email and event name, not the full customer record. The fourth consideration is monitoring and auditing. Run history and diagnostic logs must be handled carefully because workflow inputs and outputs may contain personal information. Sensitive fields should be secured, and logs should be retained only as required by policy. Finally, network security should be considered by using private endpoints, restricted access and secure connector configuration where appropriate.

#### Event Grid Combined with Other Services

Azure Event Grid can create robust workflows because it decouples event publishers from event consumers. A service publishes an event that describes something that happened, and subscribers react to that event independently. Microsoft (2026h) describes Event Grid as an event routing service that supports event-driven architecture and integration across Azure services.

In EventEase, a booking created in the web application could publish a `BookingCreated` event to Event Grid. Azure Functions could subscribe to that event to send a confirmation email, generate a receipt or update an analytics table. This keeps the booking creation request fast because additional processing happens asynchronously.

Event Grid can also work with Blob Storage. When an event or venue image is uploaded, Blob Storage can publish a `BlobCreated` event. A Function or Logic App can then generate thumbnails, scan metadata or update a search index. Event Grid can also route events to Azure Service Bus for more durable queue-based processing when downstream systems may be temporarily unavailable. Combining Event Grid with Functions, Logic Apps, Blob Storage and Service Bus creates workflows that are scalable, resilient and easier to extend because new subscribers can be added without rewriting the core application.

### C.4 Project Reflection

Developing EventEase across Parts 1, 2 and 3 helped me understand that cloud development is more than publishing a web application to Azure. In Part 1, the main focus was building a functional ASP.NET Core MVC application with a relational database structure. This taught me the importance of designing the schema around business rules. The venue, event and booking tables had to support the core requirement of preventing double bookings and managing relationships clearly.

In Part 2, the project became more cloud-focused because images moved from simple URLs to Azure Blob Storage. This was one of the most challenging parts of the POE because I had to understand how Blob Storage accounts, containers, connection strings, uploaded files and saved image URLs work together. It was also very instructive because it showed me why cloud applications should separate compute, structured data and file storage. Images are better stored as blobs, while SQL should store the structured business data and the blob URL. I also learned the importance of configuration management because local development, Azure App Service and Azure Storage all require different settings without committing secrets to source control.

Part 3 showed the value of designing for future requirements. The event type lookup and venue availability field made the booking overview more useful for real booking specialists. The advanced filters also showed how a well-designed data model makes later features easier to add. Instead of redesigning the system, the controller could compose optional filters over the existing booking detail query.

The main challenges were understanding and setting up Azure services, implementing Blob Storage correctly, deployment configuration, database evidence and keeping the implementation aligned with the rubric. Azure App Service and Azure SQL Database make hosting easier, but I still had to learn how the Azure Portal, App Service configuration, SQL connection strings, database schema updates, seeded data and storage containers fit together. Although this was difficult at first, it was very instructive because it helped me understand the practical steps behind deploying a cloud-based application instead of only learning the theory. The SQL Query Editor screenshots are important because they provide direct evidence that the Azure database was updated, not only the local codebase.

The most important lesson I learned is that cloud-based applications should be designed around managed services, security, scalability and evidence. Azure App Service hosts the application, Azure SQL protects relational data, and Azure Blob Storage stores images separately. A strong architecture keeps each service focused on the role it handles best. If I were improving the project further, I would add EF Core migrations from the start, configure Azure Key Vault for secrets, add automated tests for booking validation, and consider Event Grid or Logic Apps for future notification workflows.
